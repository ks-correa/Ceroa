# EP-02 — Registro y acceso a Ceroa

Implementación de HU-003 a HU-009 sobre React/TypeScript, Spring Boot/Security, PostgreSQL y Flyway existentes. La verificación real con Google/Microsoft está pendiente por ausencia de credenciales externas; no se declara la épica completada.

## Cambios

- Registro local con nombre, correo, celular, nacimiento, contraseña, confirmación y ambos consentimientos. Validación en navegador y servidor; mayoría de edad según America/Bogota; BCrypt con límite de 72 bytes. Datos personales editables se conservan ante error; ambas contraseñas se limpian.
- Login con mensajes indistinguibles para cuenta inexistente y contraseña incorrecta. Sesiones existentes reutilizadas: cookie HttpOnly/SameSite=Lax, token aleatorio cuyo hash se almacena en PostgreSQL, CSRF obligatorio y comprobación `/auth/me` al recargar.
- OAuth2 Authorization Code / OpenID Connect real mediante Spring Security. Identidades por proveedor + issuer + subject, sin vinculación automática por correo. No se persisten tokens del proveedor. Datos faltantes y consentimientos se recogen antes de crear usuario/sesión Ceroa; el estado temporal vence en 10 minutos. Cancelación/errores invalidan ese estado.
- `initialSetupComplete` proviene del backend. Cuentas nuevas van a Configuración financiera inicial pendiente, sin generar perfiles financieros ficticios; cuentas configuradas van a Inicio. La pantalla pendiente no permite navegar a las vistas financieras. No se desarrolla la configuración financiera en esta épica.
- Recordar correo guarda exclusivamente `ceroa_remembered_email`, con autorización. Desmarcar elimina la preferencia inmediatamente. No almacena contraseñas ni tokens en Web Storage.
- Formularios divididos en componentes y hooks; etiquetas, errores asociados, foco visible, controles de contraseña y estados de carga. Verificados a 375, 768 y 1440 px.

## Archivos principales

- `frontend/src/components/auth/`: LoginView, RegisterView, ExternalRegistrationView, AuthFields, AuthLayout, ProviderButtons, hooks y validación.
- `frontend/src/services/authService.ts`, `api.ts`, `context/AppContext.tsx`, `App.tsx`: contrato y acceso confirmado por backend.

- Pruebas: `AuthIntegrationTest`, `OAuthFlowTest`, `frontend/src/components/auth/auth.test.tsx`, `frontend/e2e/auth.spec.ts`.

## Migraciones

V5 agrega estado de configuración, fechas de consentimiento y `external_identities` con restricciones de identidad y relación a usuario. Conserva cuentas/tablas existentes y solo marca la cuenta demo ya configurada como completa; no infiere configuración de perfiles ficticios históricos.

V6 agrega unicidad de correo sin distinguir mayúsculas (`lower(email)`). Si una base preexistente contiene duplicados que solo difieren en mayúsculas, la migración falla para evitar fusionar o eliminar cuentas automáticamente.

V1–V6 se aplicaron y validaron mediante Flyway sobre PostgreSQL 18.6 aislado, puerto 55432, base `ceroa_ep02`. La base habitual en 5432 no se modificó: las credenciales de ejemplo no permiten acceder a ella. Docker Compose del proyecto sigue usando PostgreSQL 17; Flyway emitió aviso de versión más reciente para PostgreSQL 18, sin errores de migración o pruebas.

## Configuración externa pendiente

Definir variables del backend (o `.env` local ignorado, cargado al ejecutar desde `backend`):

| Variable | Valor requerido |
| --- | --- |
| GOOGLE_CLIENT_ID | Client ID de aplicación web OAuth de Google |
| GOOGLE_CLIENT_SECRET | Secreto correspondiente, solo backend |
| MICROSOFT_CLIENT_ID | Application/client ID de Entra |
| MICROSOFT_CLIENT_SECRET | Valor del secreto de aplicación, solo backend |
| MICROSOFT_TENANT_ID | UUID del tenant autorizado; no `common` ni `organizations` |
| OAUTH_REDIRECT_BASE_URL | URL pública del backend; local: `http://localhost:8080` |
| FRONTEND_URL | Origen exacto del frontend; local: `http://localhost:3000` |
| SESSION_SECURE_COOKIE | `true` con HTTPS en producción |
| DB_URL / DB_USERNAME / DB_PASSWORD | Conexión PostgreSQL real autorizada |

En Google Cloud crear cliente **Web application**, configurar consentimiento y usuarios de prueba si aplica, y registrar exactamente `http://localhost:8080/login/oauth2/code/google` como URI de redirección local.

En Entra registrar una aplicación **Web**, habilitar los tipos de cuenta admitidos por el tenant configurado, crear el secreto y registrar exactamente `http://localhost:8080/login/oauth2/code/microsoft`. La integración mantiene validación estricta del issuer del tenant; no implementa aceptación indiscriminada de tenants. Solicita scopes `openid profile email`. Microsoft puede omitir email: se solicita como dato de contacto, nunca se usa para vincular cuentas existentes.

Para despliegue reemplazar los callbacks por `${OAUTH_REDIRECT_BASE_URL}/login/oauth2/code/{google|microsoft}` y registrar esas mismas URLs en los proveedores. Frontend y backend deben usar HTTPS y pertenecer al mismo sitio para las cookies SameSite=Lax; `FRONTEND_URL` controla CORS exacto. No guardar secretos en variables `VITE_*`. La sesión HTTP OAuth es temporal en memoria: en varias instancias se requiere afinidad durante el retorno OAuth o un repositorio de sesión compartido.

Un proveedor sin todas sus variables devuelve un mensaje de indisponibilidad al pulsar su botón; el registro local sigue funcionando. No hay simulaciones en producción. Las identidades de prueba se usan exclusivamente dentro de tests.

Referencias de implementación: [configuración OAuth2 Login de Spring Security](https://docs.spring.io/spring-security/reference/servlet/oauth2/login/advanced.html) y [claims de ID token de Microsoft](https://learn.microsoft.com/en-us/entra/identity-platform/id-token-claims-reference).

## Ejecución y verificación

```powershell
# Backend: conexión PostgreSQL configurada, migraciones automáticas al arrancar
cd backend
.\mvnw.cmd package
java -jar target/ceroa-backend-0.1.0-SNAPSHOT.jar

# Frontend (otra terminal)
cd frontend
npm ci
npm run lint
npm test
npm run build
npm run dev
```

Integración PostgreSQL en una base de prueba desechable (no ejecutar contra producción):

```powershell
cd backend
$env:PG_TEST_URL = 'jdbc:postgresql://127.0.0.1:55432/ceroa_ep02'
$env:PG_TEST_USERNAME = 'ceroa_ep02'
# PG_TEST_PASSWORD según la instancia
.\mvnw.cmd test '-Dspring.profiles.active=postgres-test' '-Dtest=AuthIntegrationTest,OAuthFlowTest'
```

E2E requiere backend en `http://localhost:18080` conectado a base desechable con migraciones y cuenta demo, `FRONTEND_URL=http://localhost:3000`, proveedores sin credenciales. Playwright arranca Vite en 3000. Las pruebas crean usuarios de prueba y comprueban el endpoint de logout que ya existía, sin implementar EP-03.

```powershell
cd frontend
npx playwright install chromium
npm run test:e2e
```

Resultados de EP-02: 42 tests backend (incluye 27 de autenticación y 6 de OAuth), 33 pruebas de autenticación/OAuth también sobre PostgreSQL; 32 frontend; 6 E2E Chromium. TypeScript y build frontend pasan. Verificación de cookies, persistencia real, restauración, ambos destinos, errores y preferencia. Las pruebas OAuth usan principales verificados de prueba para comprobar nuestra lógica y rechazan callbacks sin state válido; **no verifican un login real contra Google/Microsoft**.

Durante la revisión final aparecieron modificaciones concurrentes de recuperación de contraseña y V7 ajenas a esta tarea, que inicialmente rompían la compilación del árbol compartido. No se eliminaron ni se implementaron como parte de EP-02. Se conservó una copia de validación de EP-02 en `tmp/ep02-validation` (ignorada por Git), excluyendo esos archivos/columna de recuperación, para comprobar el alcance V1–V6. Los resultados de esa copia no certifican cambios concurrentes posteriores del árbol compartido.

La última comprobación del árbol compartido también pasó: `mvnw package` con 58 tests backend y `npm run lint`/`npm test` con 51 tests frontend, incluyendo pruebas agregadas concurrentemente de otras épicas. La validación E2E de EP-02 sigue siendo de 6 casos contra el backend aislado V1–V6. Se detuvieron el backend de prueba y la instancia PostgreSQL aislada al terminar; no se dejó un servicio adicional ejecutándose.
