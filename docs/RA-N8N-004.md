# RA-N8N-004: briefing y recordatorios programados

Requerimiento independiente de RA-N8N-001, RA-N8N-002 y RA-N8N-003.
Estado: análisis del backend y plan registrados. Workflow, APIs de entrega y
persistencia de estados pendientes; no hay programación ni envío activo.

## Capacidades existentes y faltantes

- UpcomingDueService calcula fechas, importes, estado e hitos exactos SEVEN_DAYS,
  THREE_DAYS y DUE_TODAY. n8n debe filtrar estos valores, sin calcularlos por su cuenta.
- NotificationService crea eventos internos al consultar el centro de notificaciones;
  usa DUE_MILESTONE + deuda + fecha + hito, asociado al usuario.
- El índice actual sobre user_id/event_key no es UNIQUE: una consulta previa no basta
  para garantizar ausencia de duplicados con dos ejecuciones simultáneas.
- Notification conserva lectura/canal, pero no estados de entrega, intentos, backoff,
  bloqueo de envío ni mensaje de Telegram. Leído no equivale a enviado.
- registerExternalReminder no revalida el evento y no está expuesto como API autorizada.
  La ruta de navegador external-reminder sigue denegada; no habilitarla sin el contrato nuevo.
- No existe aún vínculo verificado de Telegram ni consentimiento por canal. Un token
  de automatización personal no permite enumerar ni operar sobre todos los usuarios.

## Orquestación propuesta

Schedule Trigger (America/Bogota, horario pendiente) → API de candidatos elegibles
→ Switch por hito suministrado por backend → API de revalidación/reserva transaccional
→ evento interno idempotente → texto canónico con valores de backend, redacción IA
opcional → revalidación inmediatamente antes del envío → Telegram → API de resultado.

Las APIs son nuevas y se definirán antes de generar el workflow; no asumir que existen.
El worker tendrá una credencial de servicio dedicada y permisos limitados a recordar
y registrar entregas, sin CRUD financiero ni acceso SQL. El backend decide qué usuarios
y canales puede atender. Paginación y reservas permiten varias ejecuciones sin competir.

La clave lógica es usuario + deuda + fecha de vencimiento + hito. Debe existir una
restricción única persistente en Spring Boot/PostgreSQL, compartida con los eventos
internos ya generados al abrir Ceroa. No mantener una segunda deduplicación en n8n que
ignore el centro de notificaciones. Antes de añadir UNIQUE, revisar y reconciliar posibles
duplicados existentes; no eliminar registros sin un plan revisable.

## Revalidación y estados

Spring Boot revalida propietario, estado/saldo, fecha de vencimiento, hito, cuenta activa,
plan efectivo, vínculo Telegram y consentimiento. Cambios o eliminación invalidan
reservas pendientes. Las operaciones de pago/eliminación actualizarán el estado de los
eventos y la API vuelve a comprobarlo antes de enviar, manteniendo los servicios financieros.

Usar un evento interno con entregas por canal para distinguir notificación visible en
Ceroa de entrega externa. Estados públicos por entrega: enviado, pendiente de reintento,
invalidado y fallido. La reserva/bloqueo temporal es un detalle interno. Sin Telegram
autorizado puede existir evento IN_APP, sin inventar un envío externo exitoso.

Solo una confirmación exitosa de Telegram permite marcar su entrega enviada; guardar
el message_id y momento de entrega en backend. Guardar resultado también es idempotente.
Fallo de backend tras Telegram no debe repetir directamente el envío: reintentar primero
el registro del mismo resultado. Timeout ambiguo de Telegram requiere tratamiento separado;
su envío no forma una transacción con PostgreSQL y no se puede prometer exactamente una
entrega externa ante cualquier caída. No confundir idempotencia del evento con esa garantía.

Es imposible impedir todo cambio financiero entre la última revalidación y un envío remoto.
Reducir esa ventana y conservar la instantánea/momento de validación; no afirmar que ambos
sistemas tienen una transacción atómica. Pagos posteriores invalidan pendientes; no borran
evidencia de avisos efectivamente entregados antes de ese pago.

## Reintentos y Error Workflow

Definir máximo de intentos, backoff con jitter y vencimiento del evento en backend.
No generar hitos de 6, 2 días o vencimientos pasados como recuperación de un horario perdido.
La política de entrega tardía de un evento ya creado debe definirse explícitamente;
por defecto no enviar avisos cuyo texto temporal haya dejado de ser válido.

Revalidación/API no disponible: no enviar; conservar pendiente si sigue dentro de plazo.
429 de Telegram respeta retry_after; fallos permanentes de canal terminan fallidos;
deuda pagada/eliminada, fecha cambiada o permiso revocado termina invalidado.
Error Workflow informa el fallo operativo sin registrar datos financieros, tokens ni
cuerpos de mensajes. El scheduler procesa de nuevo pendientes desde backend: no depende
solo de que Error Trigger llegue a ejecutar otra llamada.

## IA, permisos y briefing

La IA solo redacta introducción/cierre. Monto, fecha, hito, estado y progreso se insertan
de forma determinista desde los datos actuales del backend. Si Gemini falla, usar una
plantilla canónica; no es necesario perder un recordatorio correcto por un fallo de IA.

Plus/premium y consentimiento se comprueban al preparar y antes de entregar. Registrar
planRestricted no sustituye bloquear una función restringida. Falta concretar qué funciones
son Plus y qué recordatorios internos están disponibles para todos; aplicar PlanAccessService.

El briefing periódico usa dashboard/progreso/hitos suministrados por Spring Boot; no sumar
deudas ni inferir logros en el modelo. Tiene clave propia por usuario + tipo de resumen +
período, separada de los recordatorios 7/3/0. Horario, período y consentimiento pendientes.

## Operación y pruebas de aceptación

n8n local solo ejecuta el horario mientras la computadora y Docker están encendidos.
Para servicio continuo se requiere alojamiento disponible; Supabase aloja la base, no
ejecuta por sí mismo este workflow de n8n.

- Días 7/3/0 generan eventos; 8/6/4/2/1/-1 no generan hitos.
- Dos workers simultáneos y reejecución: un evento y una reserva por clave lógica.
- Pago/eliminación/cambio de fecha o revocación de permiso antes del envío: invalidado.
- Evento creado desde la interfaz Ceroa y luego por scheduler: no se duplica.
- Telegram 429/5xx/permanente, backend caído y fallo al guardar resultado: estados correctos.
- Timeout de entrega ambiguo: ninguna repetición automática no controlada.
- IA modifica cifras o falla: plantilla determinista, sin alterar datos.
- Resumen repetido del mismo período: una clave propia; sin cambiar obligaciones.
