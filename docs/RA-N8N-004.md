# RA-N8N-004: briefing y recordatorios programados

Estado: implementado y activo en el entorno local con Supabase, el 27 de septiembre de 2026.
RA-N8N-003 quedó completado y aceptado por el usuario antes de iniciar este requerimiento.

## Comportamiento y consentimiento

El scheduler `ceroaReminders04` revisa cada cinco minutos en America/Bogota. Spring Boot
crea exclusivamente los hitos SEVEN_DAYS, THREE_DAYS y DUE_TODAY de UpcomingDueService.
No inventa hitos de 6/2 días ni recupera días completos perdidos. Los eventos internos
están disponibles para todos los planes; Telegram y briefing requieren Plus efectivo,
cuenta activa, vínculo privado verificado y consentimiento específico de cada cuenta.

Perfil → Avisos y resumen por Telegram permite autorizar recordatorios y resumen por
separado, escoger hora de Colombia y frecuencia semanal (lunes) o mensual (día 1).
Valores iniciales: 08:00 y semanal. Vincular el bot para consultas no autoriza estos
avisos: ambos consentimientos empiezan desactivados. Revincular exige consentimiento nuevo.

El briefing es una instantánea actual del dashboard: saldo registrado, deudas activas,
estrategia, pagos requeridos, próximo vencimiento y pagos registrados si hay evidencia.
No afirma que los pagos acumulados correspondan exclusivamente a la semana o al mes.
Los textos son canónicos, con cifras de backend y separadores colombianos. No dependen
de Gemini; la IA opcional no calcula ni altera cifras. Se escapa HTML antes de Telegram.

## APIs y aislamiento

Schedule Trigger → preparación paginada → pendientes → reserva → revalidación → Telegram
→ registro del resultado. La credencial privada X-Ceroa-Reminders es independiente de
asistente, documentos, RAG y automatizaciones personales. No permite CRUD financiero,
SQL ni acceso a otros endpoints. El backend decide propietarios y destinatarios.

| API | Propósito |
| --- | --- |
| GET/PUT `/api/v1/integrations/telegram/reminders` | Preferencias del usuario autenticado; PUT con CSRF |
| GET `/api/v1/integrations/telegram/deliveries` | Sus últimas 50 entregas; sin tokens o destinatarios |
| POST `/api/v1/reminder-worker/scan?page=0` | Worker exclusivo; páginas de 25 usuarios |
| GET `/api/v1/reminder-worker/candidates` | Worker exclusivo; hasta 100 pendientes |
| POST `/api/v1/reminder-worker/deliveries/{id}/reserve` | Reserva exclusiva con token |
| POST `/api/v1/reminder-worker/deliveries/{id}/dispatch` | Revalidación y autorización de un intento |
| POST `/api/v1/reminder-worker/deliveries/{id}/outcome` | Confirmación o fallo de ese intento |

Los workflows no tienen trigger público. La ruta antigua external-reminder permanece
denegada. n8n guarda credenciales cifradas y tiene desactivado guardar datos de ejecuciones.
El Error Workflow `ceroaReminderError04` emite solo un diagnóstico fijo, sin tokens,
identidades, importes ni mensajes. Funciona por la referencia del scheduler, sin activación
programada propia. La recuperación de pendientes no depende del Error Trigger.

## Supabase y deduplicación

Flyway V17 agrega reminder_preferences, scheduled_deliveries y la restricción única
notifications(user_id,event_key). No cambia migraciones anteriores ni usa PostgreSQL local.
La clave compartida con las notificaciones IN_APP es DUE_MILESTONE:deuda:fecha:hito;
el briefing tiene la clave separada BRIEFING:frecuencia:fecha. Bloqueos por usuario y
entrega, más las restricciones persistentes, evitan eventos y reservas concurrentes dobles.

La revisión previa del Supabase real encontró cero claves duplicadas. Si una instalación
contuviera copias, V17 conserva todos los registros y su lectura: archiva la clave original
en notification_duplicate_keys y asigna una clave distinta a las copias adicionales.
No elimina notificaciones para introducir UNIQUE.

## Revalidación, estados y límites

Se comprueban propietario, cuenta, plan efectivo, vínculo, consentimiento, saldo, estado,
fecha, hito y vigencia al reservar y de nuevo justo antes de enviar. Cambiar deuda/pagos
o desvincular invalida pendientes/reservados. El texto y validated_at del intento quedan
persistidos. Los datos financieros no se modifican al programar ni entregar avisos.

Estados: PENDING, RETRY, RESERVED, DISPATCHING, SENT, INVALIDATED, FAILED y AMBIGUOUS,
mostrados en español en Perfil. Leer un aviso no equivale a entregarlo. Solo Telegram
ok=true y message_id válido permite SENT y canal TELEGRAM del evento interno.

Las reservas duran tres minutos. Una reserva sin envío puede recuperarse; un despacho
vencido termina AMBIGUOUS y no se repite automáticamente. Un resultado confirmado tardío
del mismo token puede conciliarse sin reenviar. Pendientes vencen a medianoche de Colombia.
Máximo cuatro intentos efectivos, backoff de 60/120/240 segundos más jitter, respetando
un retry_after mayor. 429 y 5xx reconocidos se reintentan; bloqueos permanentes reconocidos
terminan FAILED. El nodo Telegram puede devolver solo una descripción: se reconocen
únicamente descripciones canónicas conocidas; errores desconocidos/timeouts son AMBIGUOUS.

Registrar un resultado reintenta tres veces el mismo cuerpo, sin ejecutar otra vez Telegram.
Si esos registros fallan, el despacho termina AMBIGUOUS al expirar. No existe transacción
atómica Telegram/Supabase ni garantía de exactamente una entrega ante cualquier caída.
También puede cambiar una deuda entre revalidar y el envío remoto; las confirmaciones
anteriores a un pago se conservan como evidencia y no se borran.

## Instalación y operación

```powershell
.\integrations\n8n\install-reminders.ps1
.\integrations\n8n\activate-reminders.ps1
```

La instalación genera la clave privada en .env y asocia el bot existente. La activación
construye backend/frontend, migra Supabase con Flyway, comprueba arranque y publica el
scheduler. No autoriza envíos en ninguna cuenta. Cada usuario los activa en Perfil.

n8n local programa mientras computadora y Docker estén encendidos. Supabase conserva
los estados, pero no ejecuta n8n. Para disponibilidad continua hace falta alojar n8n en
un servidor. El envío se atiende en la siguiente revisión de cinco minutos; un arranque
posterior dentro del mismo día puede procesar hitos cuyo texto todavía es válido.
