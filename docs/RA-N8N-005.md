# RA-N8N-005: centinela de sobrecapacidad con aprobación humana

Requerimiento independiente de RA-N8N-001/002/003/004.
Estado: análisis y plan registrados; no hay workflow, evaluación de riesgo ni aprobación
implementados. No se ejecutan simulaciones ni se modifican datos financieros.

## Backend existente

DashboardService devuelve pagos requeridos, disponible para deudas, cobertura parcial
y disponibilidad de datos. Su status SUCCESS/EMPTY/INSUFFICIENT_DATA describe los datos;
no es un dictamen de riesgo ni una autorización para generar una alerta crítica.
StrategyEngine detecta algunas proyecciones insuficientes, pero no existe un contrato
unificado de indicadores/condiciones/acciones del centinela. No interpretar texto libre
como regla ni inventar porcentajes o umbrales en n8n.

SimulationService ya es readOnly, verifica Plus efectivo y pertenencia de la deuda,
y delega cálculos al SimulationEngine. POST `/api/v1/simulations` es una operación
hipotética: no registra pagos ni modifica estrategia. Su contrato requiere una deuda,
estrategia y eventos opcionales; no convertirlo en una simulación global sin servicio
que la soporte. El bearer de automatización no accede a esta API de navegador.

## Evaluación y alerta

Spring Boot debe ofrecer una evaluación estructurada con fecha, versión de datos,
calidad/cobertura, indicadores válidos, condición activa, motivo y acciones permitidas.
Las reglas se definen y versionan en backend; su política funcional queda pendiente.
Ausencia de indicadores o datos parciales produce información insuficiente, nunca
una declaración automática de que el usuario está sin riesgo o en riesgo crítico.

Triggers independientes: cambios financieros confirmados por backend (evento tras
commit/outbox), evaluación programada y botón autenticado de Ceroa. No confiar en
un webhook público que declare haber ocurrido un pago o identifique otra cuenta.
Agrupar cambios consecutivos para evaluar la versión vigente y evitar alertas repetidas.
Deduplicar por usuario + condición + versión/episodio, según política backend.

n8n consulta evaluación → Switch por condición suministrada → redacción explicativa
sin herramientas financieras → alerta Telegram/FAB con indicador, valor y alternativas.
El modelo no selecciona umbrales ni añade acciones. Valores se insertan desde backend;
si el modelo falla, usar texto canónico. Minimizar información en Telegram.

## Aprobación humana

El backend mantiene un registro de aprobación con identificador impredecible,
propietario, acción de una lista cerrada, parámetros concretos/inmutables, versión
financiera, emisión, expiración y estado. Un identificador no prueba identidad:
verificar sesión web/CSRF o remitente de Telegram vinculado antes de aceptar.
No exponer una URL GET que ejecute la acción ni transportar parámetros sensibles
libremente en un callback. Los botones referencian una aprobación almacenada.

Aprobar exige que exista una operación pendiente vinculada inequívocamente; "ok",
memoria del agente o instrucciones en un documento no autorizan nada. Descartar
cierra la aprobación sin modificar deudas/perfil; conservar ese estado de control
no es un cambio financiero.

Al aprobar, Spring Boot revalida identidad, permisos Plus vigentes, propiedad,
acción/parámetros permitidos, expiración y versión actual de datos. Datos cambiados
invalidan la aprobación; mostrar una evaluación nueva y pedir nueva confirmación.
Consumo/reserva transaccional de un solo uso evita dos acciones por callbacks
simultáneos. Repetir el mismo callback devuelve su resultado/estado; no ejecuta de nuevo.

Estado de aprobación separado de alerta y resultado: pendiente, descartada,
expirada, invalidada, en ejecución, completada o fallida. Si falla la simulación,
conservar alerta informativa y marcar intento fallido; no reutilizar una aprobación
consumida para otra acción. Una nueva ejecución requiere nueva aprobación.

## Acción inicial permitida

Solo GENERATE_SIMULATION, disponible cuando backend autorice Plus y la deuda elegida.
Una estrategia simulada no se convierte en estrategia activa. El resultado incluye
supuestos y se etiqueta "Escenario hipotético"; INSUFFICIENT_DATA no equivale a una
simulación exitosa y requiere explicación sin inventar resultados.

Para web, usar sesión y CSRF en el circuito autorizado. Para orquestación desde
Telegram se necesita una API específica con alcance de simulación y aprobación;
no entregar un token CRUD con allowWrites=true como atajo. n8n transmite la decisión,
Spring Boot consume la aprobación y llama a SimulationService.

Modificar deudas, pagos, ingresos, perfil o estrategia queda fuera de este workflow.
Ninguna herramienta del agente puede ejecutar pagos ni acciones financieras generales.

## Pruebas de aceptación y pendientes

- Backend sin condición relevante: no alerta crítica ni acción automática.
- Indicador ausente/parcial: mensaje de datos insuficientes, no umbral inventado.
- Descartar/"ok"/otro usuario/callback manipulado/expirado: ninguna simulación o cambio.
- Plan revocado, deuda eliminada o datos cambiados tras mostrar alerta: invalidar y reconfirmar.
- Dos aprobaciones simultáneas o callback repetido: un consumo y un resultado reutilizable.
- Simulación fallida/incompleta: alerta informativa; ningún pago real ni cambio de estrategia.
- Texto de IA y números: valores del backend preservados, acciones de lista cerrada.
