# RA-N8N-005: centinela de sobrecapacidad con aprobación humana

Estado: implementado. La alerta Telegram requiere consentimiento separado, Ceroa Plus y un chat privado vinculado. El usuario aprueba una simulación desde la sesión web de Ceroa; el bot no interpreta mensajes como autorización.

## Política financiera

Spring Boot aplica `BUDGET_OVER_CAPACITY_V1`: suma los pagos exigibles de las obligaciones activas y compara con el presupuesto que el usuario asignó a deudas. Solo produce `OVER_CAPACITY` cuando `requiredPayments > budget`. Un presupuesto de cero es válido. El backend devuelve versión financiera, fecha, calidad, condición, motivo, cifras y acciones permitidas. Faltan datos (`UNKNOWN` / `INSUFFICIENT_DATA`) si no hay perfil, no hay deudas, la cantidad declarada difiere de la registrada, falta el pago exigible de alguna deuda o el perfil/alguna obligación activa no se actualizó durante 90 días. Estar dentro del presupuesto no descarta otros riesgos financieros.

Las operaciones confirmadas de deuda, pago, perfil y estrategia incrementan la versión en la misma transacción; un rollback revierte el incremento. Tras el commit se evalúa la nueva versión para mostrar la alerta en la app. El workflow independiente vuelve a evaluar cada cinco minutos y recupera eventos pendientes tras un fallo. El botón Centinela permite evaluar manualmente. Una alerta in-app se crea una sola vez por episodio continuo de sobrecapacidad; el episodio se cierra cuando la condición deja de cumplirse o la calidad resulta insuficiente.

## Entrega y aprobación

El workflow `ceroaSentinel05` carece de trigger público y usa `X-Ceroa-Sentinel`, una credencial propia sin acceso a CRUD financiero. Spring Boot prepara, reserva y revalida cada alerta antes del envío. El texto y todas las cifras proceden del backend; n8n solo escapa y entrega el texto, sin usar el modelo para decidir umbrales o acciones. Los fallos con resultado de envío ambiguo no se reenvían automáticamente. El aviso Telegram minimiza datos y pide revisar las opciones en la aplicación. El consentimiento para este canal es distinto al de recordatorios.

La única acción permitida es `GENERATE_SIMULATION` para Ceroa Plus. El usuario elige deuda y estrategia, revisa una autorización de diez minutos y pulsa **Aprobar simulación** en Ceroa. La sesión y CSRF identifican al propietario. El backend vuelve a verificar plan, deuda, episodio, versión y condición, y reserva la aprobación de un solo uso antes de llamar a `SimulationService`. La simulación es hipotética y no registra pagos ni cambia la estrategia. Se distinguen los estados pendiente, descartado, expirado, invalidado, en ejecución, completado y fallido; una repetición devuelve el estado ya guardado. Una ejecución inconclusa que supera el vencimiento se marca fallida al consultarse.

## Instalación local

1. `powershell -ExecutionPolicy Bypass -File integrations/n8n/install-sentinel.ps1` genera el workflow, crea una clave privada en `.env` y asocia las credenciales cifradas de n8n, sin publicar ni enviar.
2. `powershell -ExecutionPolicy Bypass -File integrations/n8n/activate-sentinel.ps1` activa la función, reconstruye backend/frontend para aplicar V18 en Supabase, publica el scheduler y reinicia n8n.
3. Cada usuario habilita los avisos de Telegram en el panel **Centinela** si tiene Plus y su chat privado vinculado. La alerta de la app no exige este consentimiento.

Las pruebas de integración cubren datos ausentes/antiguos, deduplicación, descarte, otra cuenta, separación de la credencial del worker y consumo simultáneo de la aprobación. Ninguna prueba envía un mensaje real.
