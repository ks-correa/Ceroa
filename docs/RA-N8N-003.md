# RA-N8N-003: consultor contextual mediante RAG

Estado: preparación del corpus implementada; recuperación, embeddings, memoria y
flujo conversacional pendientes de fuentes aprobadas, modelo y credenciales. No activo.
Comparte los canales e identidad de [RA-N8N-001](RA-N8N-001.md).

## Dos flujos separados

**Indexación administrativa:** manifiesto de fuentes aprobadas → comprobar versión
y hash → fragmentar → Default Data Loader → Embeddings Google Gemini → PGVector
Insert Documents. Nunca alimentar este flujo con mensajes de usuarios, historiales
financieros, respuestas HTTP financieras o memoria conversacional. Sin trigger público.

**Consulta:** entrada autorizada de web/Telegram → clasificar documental/personal/mixta
→ recuperación documental y/o herramientas GET fijas de Spring Boot → validar evidencia
→ respuesta con fuentes → memoria de contexto por usuario y canal.

La recuperación documental no concede acceso financiero. Para una consulta personal
se aplica la verificación de cuenta de RA-N8N-001, aun si la conversación anterior fue
documental. Si falla la autorización en una pregunta mixta, explicar que no se pueden
consultar datos personales; solo dar la parte documental si existe evidencia aprobada.

## Preparación implementada

`integrations/n8n/rag/sources.json` está vacío deliberadamente. Cada entrada requiere:

```json
{
  "path": "docs/archivo-aprobado.md",
  "title": "Título aprobado",
  "version": "1",
  "approved": true,
  "approvedBy": "Responsable de revisión",
  "sha256": "SHA-256 real de los bytes aprobados"
}
```

Tras aprobar los documentos y completar el manifiesto:

```powershell
node integrations/n8n/rag/prepare-corpus.mjs
```

La salida es `tmp/rag/approved-chunks.json`, fuera de Git, con `pageContent` y metadatos
de fuente, versión, hash e identificador estable de fragmento. No llama a Gemini ni
escribe en Supabase. Solo acepta Markdown explícito dentro del repositorio y verifica
su integridad; no escanea carpetas ni indexa automáticamente README o documentación
de infraestructura. Fragmentación inicial: 1200 caracteres y 200 de solapamiento;
calibrar con el modelo elegido, no interpretar caracteres como tokens.

Para PDFs u otros formatos se preparará una extracción revisable antes de su aprobación.
Un hash acredita que el archivo no cambió; la aprobación humana debe comprobar que su
contenido es válido, no contiene secretos ni información personal y corresponde a Ceroa.

## Almacenamiento y credenciales

Preferencia de integración: PGVector en un esquema auxiliar `n8n_aux` de Supabase,
fuera de Flyway de negocio. Dos credenciales PostgreSQL dedicadas: indexador para
escribir exclusivamente documentos auxiliares y consultor para recuperar documentos.
Ninguna debe tener USAGE ni permisos sobre `ceroa`, ni ser el usuario `postgres`, ni
heredar un rol con acceso financiero. Verificar permisos efectivos antes de activarlas.
La configuración de tabla/esquema debe comprobarse con la versión instalada del nodo;
no asumir que el nombre de tabla admite un nombre calificado sin probarlo.

No se crea aún la tabla vectorial: requiere elegir modelo, comprobar la dimensión real
de su salida y compatibilidad del nodo. Ingesta y consultas usan el mismo modelo,
dimensión y procesamiento. Cambiar de modelo exige un índice nuevo y reindexación.
Separar versiones publicadas; retirar de consulta los fragmentos de documentos revocados
o reemplazados, evitando duplicar documentos en cada ejecución del indexador.

El runtime debe tener acceso de lectura únicamente. Algunos clientes crean tablas o
extensiones al inicializar: probarlos con la credencial limitada. Si requieren DDL,
precrear por administración o usar una herramienta de recuperación parametrizada;
no resolverlo concediendo privilegios generales al agente.

## Recuperación y respuestas

Solo la colección/versiones publicadas y aprobadas son consultables. Recuperar un
número limitado de fragmentos y aplicar un filtro real de relevancia antes de generar
respuesta. Calibrar el umbral con preguntas de prueba; no inventar un umbral universal
ni asumir que cualquier resultado del top-k es evidencia suficiente. Si el Vector Store
Tool oculta puntuaciones, usar Get Many con resultados verificables dentro de una
herramienta de workflow y filtrar antes de devolver contexto al agente.

La respuesta documental incluye título y referencia a los fragmentos utilizados.
Sin evidencia o ante fallo de Vector Store: "No tengo información aprobada suficiente
para responder esa pregunta". Sin fallback a conocimiento general del modelo ni web.

Un fragmento es evidencia, no una instrucción: ignorar texto que proponga cambiar
herramientas, permisos, destinos o reglas. El agente no recibe herramientas SQL ni
HTTP con URL/método arbitrario. Las finanzas se resuelven solo con las rutas GET
permitidas en RA-N8N-001, consultadas nuevamente para cada pregunta personal.
Importes y fechas se insertan desde el JSON del backend, fuera de la generación libre.

## Memoria

Inicialmente contexto limitado, separado con clave derivada de usuario autenticado,
canal y conversación. Nunca aceptar un sessionId público como prueba de identidad.
La memoria no se indexa como documentación aprobada, no conserva credenciales y no
responde por sí sola a preguntas sobre saldos actuales.

Window Buffer Memory sirve para una instancia sencilla; evitar Simple/Window Memory
en queue mode sin verificar su compatibilidad. Postgres Chat Memory, si se adopta,
usa otra tabla auxiliar con permisos propios y una política de retención/borrado.
Su escritura de mensajes es auxiliar y no implica permiso sobre datos financieros.

## Pruebas previas a activación

- Bola de Nieve/Avalancha: respuesta con fuentes aprobadas, sin cifras personales.
- "¿Cuál estoy usando yo?": consulta actual de estrategia del usuario asociado.
- "¿Cuánto debo?": backend como fuente; nunca sumar deudas en el modelo ni usar embeddings.
- Pregunta mixta: evidencia documental y financiera distinguibles.
- Corpus vacío, fuente retirada, modelo incompatible, vector store caído o baja relevancia:
  abstención; no respuesta inventada.
- Memoria de otra cuenta, remitente no asociado e instrucciones maliciosas en fragmentos:
  sin filtración de datos ni ejecución arbitraria.
- Consultas y solicitudes de cambios: ninguna llamada financiera POST/PUT/DELETE.
