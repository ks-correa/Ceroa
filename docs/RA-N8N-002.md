# RA-N8N-002: ingestor de documentos financieros

Requerimiento independiente de RA-N8N-001 (asistente) y RA-N8N-003 (RAG).
Estado: contrato JSON y prompt preparados a partir de DebtRequest; extracción,
upload autenticado y pantalla de revisión pendientes. No hay workflow activo ni guardado automático.

## Contrato y recorrido

Ceroa → Spring Boot (sesión + CSRF, validar archivo/operación/propiedad) → Webhook
privado autenticado de n8n → extraer contenido según formato → modelo sin herramientas
→ Structured Output Parser → verificar evidencia/contrato → borrador editable en Ceroa.

El esquema esperado es una versión fija seleccionada por el servidor, nunca un esquema
arbitrario suministrado al modelo por el cliente. El identificador de cuenta, operación
create/update y deuda destino proceden de la solicitud autorizada, no de la extracción.
Para actualizar, Spring Boot verifica primero que la deuda pertenece al usuario.

El flujo no contiene HTTP Request de escritura ni credencial financiera con permisos
de modificación. Tras revisar, el usuario pulsa Guardar en Ceroa: se utiliza el circuito
existente POST `/api/v1/debts` o PUT `/api/v1/debts/{id}`, con sesión y CSRF. Spring Boot
mantiene todas sus validaciones, límites de plan y reglas del tipo de obligación.
No hace falta que n8n intervenga en el guardado posterior.

## Esquema del borrador

Archivo: `integrations/n8n/document-ingestion/draft.schema.json`.
Usa nombres reales de `DebtRequest`: entity, type, currentBalance, interestRate,
monthlyPayment, nextDueDate, etc. Todos son nullable aunque el backend requiera algunos
al guardar. El borrador no es un DebtRequest listo para persistir.

Incluye `draft`, `evidence` (campo, cita literal, ubicación) y `warnings`. Una modalidad
desconocida de tasa no se convierte en NONE. Una cuota ausente no se convierte en cero.
No inferir name ni campos específicos dentro de details; estos requieren selección y
revisión del usuario o una ampliación de esquema por tipo de deuda.

El Structured Output Parser valida estructura, no prueba veracidad. Después debe
verificarse que cada campo no nulo tenga evidencia presente en el texto extraído.
Ambigüedad o contradicción elimina la propuesta afectada (null) y produce una advertencia.
Las citas se tratan como texto, nunca HTML ni instrucciones. No usar un reparador de JSON
que complete campos faltantes; ante salida inválida devolver error y opción manual.

El nombre personalizado, tipo, saldo actual y tipo de tasa son obligatorios en el DTO.
Los demás requisitos financieros dependen de DebtValidator y del tipo de obligación;
no replicarlos como reglas de negocio en n8n. Datos faltantes no son un fallo de guardado:
se devuelve borrador parcial para completar; ninguna API de persistencia se llama.

## Soporte real de formatos

| Formato | Procesamiento |
| --- | --- |
| PDF con texto | Extract from File, operación PDF |
| PDF escaneado | Requiere OCR; si no está configurado, indicar registro manual |
| XLSX | Extract from File, operación XLSX; preservar hoja/celda y no recalcular fórmulas |
| DOCX | No soportado directamente por Extract from File; requiere extractor adicional |

Para DOCX se propone un servicio local de extracción OOXML separado (texto y tablas),
sin macros ni acceso a URLs externas. No renombrar DOCX a PDF ni pasarlo como texto plano.
No seleccionar una hoja XLSX arbitrariamente ni unir varias obligaciones en una sola.
Archivos protegidos, corruptos o formatos incompatibles permiten continuar manualmente.

## Seguridad y revisión

Validar MIME y contenido real, tamaño, páginas/hojas y expansión de ZIP para DOCX/XLSX.
Definir límites operativos antes de activar; no truncar documentos silenciosamente.
Archivo original y contenido extraído son sensibles: sin pinData, logs de cuerpo ni
historial de ejecuciones; comprobar también almacenamiento binario y limpieza de temporales.
No indexarlos en RAG ni guardarlos en memoria conversacional. Mantener separadas las
credenciales del webhook y del modelo. Confirmar antes de activar el envío de información
financiera al proveedor elegido y su política de tratamiento/retención.

El formulario actual aplica defaults (p. ej. tipo inicial, cuota/tasa cero y día 15).
La integración debe introducir estado de borrador desconocido y distinguir ausencia,
valor extraído y valor confirmado por el usuario. No reutilizar sin adaptación la
normalización actual que convierte null en cero. Para actualizar, mostrar diferencias;
un null extraído no borra valores existentes. Guardar solo el payload revisado completo.
Mostrar evidencia y advertencias junto a los campos. Cancelar no modifica nada.

## Errores y pruebas de aceptación

- Documento sin tasa: interestRate=null y rateType=null; no cero/NONE automático.
- Datos parciales: borrador parcial, advertencias y opción de completar manualmente.
- Documento con instrucciones maliciosas: ninguna API financiera ni URL del documento ejecutada.
- Salidas inválidas, archivo corrupto, OCR ausente, timeout o credencial fallida: nada guardado.
- Otro usuario o deuda ajena: rechazado antes de procesar o mostrar información.
- Cancelación: ningún POST/PUT; guardar sin completar requisitos: validación normal backend.
- Confirmación y correcciones: la API recibe lo aprobado por el usuario, no el JSON bruto del modelo.
- PDF/DOCX/XLSX de prueba sin datos reales: comparar valores y evidencia con el contenido fuente.
